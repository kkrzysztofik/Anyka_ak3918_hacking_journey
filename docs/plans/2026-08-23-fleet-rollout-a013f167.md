# Fleet Rollout of `a013f167` Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Also load skill `anyka-firmware-upgrade` before Task 2, and `anyka-remote-debugging` for every telnet step.

**Goal:** Ship `main` @ `a013f167` to all four AK3918 cameras via the A/B upgrade path, and clear four pieces of device-local config drift on `.127` and `.146`.

**Architecture:** One `bundle.tar` serves all four cameras (identical boards). Cameras are upgraded strictly sequentially — `.198` → `.146` → `.121` → `.127` — with a full verification gate between each. On the three exFAT cameras the inactive slot is deleted with `busybox rm -rf` before upload, which sidesteps the old applier's `rename`-onto-existing-dir bug regardless of which applier version is running. Device-local config edits happen *before* the upload so the upgrade's own reboot activates them.

**Tech Stack:** Rust (armv5te-unknown-linux-uclibceabi), vendored crosstool-NG toolchain, busybox on-device, `PUT /api/update` over HTTP Basic, ssh jumphost at `root@192.168.3.137`.

**Design:** `docs/plans/2026-08-23-fleet-rollout-a013f167-design.md`

> **Version stamp correction (execution, 2026-08-23):** the rollout does not ship
> `a013f167`. Two things moved it: committing this plan and its design, and then
> `fix/www-typecheck-ts7`, which was required because `main` could not build a
> bundle at all (the WebUI type-check fails under TS 7 and no CI workflow runs
> it). **Wherever this plan says `a013f167` as an expected version, read the stamp
> printed by Task 1 Step 4** — that check against the built artifact is
> authoritative, not this note. The bundle path is `/tmp/bundle-fleet.tar`.
>
> Note that `SD_card_contents/*.bin` and `onvif/.build-version` are tracked files

> `-dirty`. `git checkout -- SD_card_contents/` before building to get a clean
> stamp. This is why the whole fleet currently runs `-dirty` versions.

## Conventions used throughout

**Never run a device command without knowing which camera answered.** A stale ssh
forward silently wins the local port, and every "`.121`" command then lands on
`.146` with plausible-looking output. Per-camera local ports:

| Camera | Local port | Tunnel |
|---|---|---|
| 192.168.2.198 | n/a — direct | none |
| 192.168.30.121 | 12421 | `ssh -f -N -L 12421:192.168.30.121:24 root@192.168.3.137` |
| 192.168.30.146 | 12446 | `ssh -f -N -L 12446:192.168.30.146:24 root@192.168.3.137` |
| 192.168.30.127 | 12427 | `ssh -f -N -L 12427:192.168.30.127:24 root@192.168.3.137` |

Telnet command form (`uv run` is mandatory — a hook rejects bare `python3`):

```bash
# direct (.198)
uv run python3 scripts/debugging/cam_exec.py --host 192.168.2.198 'CMD'
# tunnelled (.121/.146/.127)
uv run python3 scripts/debugging/cam_exec.py --host 127.0.0.1 --port 124NN 'CMD'
```

HTTP against a `192.168.30.x` camera must originate on the jumphost — the dev box
has no route:

```bash
ssh -o BatchMode=yes root@192.168.3.137 'curl -s ... http://192.168.30.NNN/...'
```

`CAMERA_PASS` must be exported in the shell before Task 2. It is never passed in
argv.

**Step 5: Confirm the size is sane**


Expected: roughly 19–20 MB. The device ceiling is 64 MB; a bundle over that gets
HTTP 413.

## Task 2: Upgrade `.198` (canary, direct, vfat)

`.198` is the canary: direct reach, vfat (never affected by the applier bug), and
physically accessible if it goes wrong. **No slot prep** — vfat renames onto an
existing directory just fine.

**Step 1: Record the pre-upgrade state**

```bash
uv run python3 scripts/debugging/cam_exec.py --host 192.168.2.198 \
  'ifconfig wlan0 | head -2 | tail -1; cat /mnt/anyka_hack/active; for s in a b; do printf "$s: "; cat /mnt/anyka_hack/slots/$s/manifest.meta 2>/dev/null | head -1; done'
```

Expected (as surveyed 2026-08-23): `inet addr:192.168.2.198`, `active` = `a`,
`a: version=b48e4847-dirty`, `b: version=2d88cf37-dirty`.

Write down the `active` value. If it is not `a`, the camera moved since the
survey — re-read the design's assumptions before continuing.

**Step 2: Upload**

```bash
cd /home/kmk/dev/anyka-dev
./scripts/upload_upgrade_bundle.sh --host 192.168.2.198 --user admin \
  --pass-file <(printf %s "$CAMERA_PASS") /tmp/bundle-a013f167.tar
```

Expected: **HTTP 202**, nothing else counts as success.

- `401` → wrong credentials.
- `409` → spool busy; see Task 6.
- `413` → bundle too large.

**Step 3: Wait out the apply window**

Wait 150 seconds. The applier polls on the supervisor tick (~60 s), stages the
inactive slot, flips `active`, and reboots; ~90–120 s of downtime is normal.

**Do not re-upload during this window.**

**Step 4: Wait for the camera to answer again**

```bash
for i in $(seq 1 30); do
  code=$(curl -s -o /dev/null -m 5 -w '%{http_code}' http://192.168.2.198/ || true)
  echo "attempt $i: $code"
  [ "$code" = "200" ] && break
  sleep 10
done
```

Expected: `200` within a few attempts. `401` also proves it is alive.

**Step 5: Verification gate**

All five must hold:

```bash
# 1. version identity
curl -su admin:"$CAMERA_PASS" http://192.168.2.198/api/diagnostics | jq -r .firmware_version
# expect: a013f167

# 2. active flipped, 3. trial cleared
uv run python3 scripts/debugging/cam_exec.py --host 192.168.2.198 \
  'cat /mnt/anyka_hack/active; ls /mnt/anyka_hack/state/trial-* 2>/dev/null; echo TRIAL_CHECK_DONE'
# expect: b   (flipped from a), and no trial-* lines before TRIAL_CHECK_DONE

# 4. ports
for p in 80 554 8080; do nc -z -w3 192.168.2.198 $p && echo "$p up" || echo "$p DOWN"; done
# expect: all three up

# 5. streams
ffprobe -v error -rtsp_transport tcp -i rtsp://admin:"$CAMERA_PASS"@192.168.2.198:554/main \
  -show_entries stream=codec_name,width,height -of csv 2>&1 | head -3
curl -s -m 8 -o /dev/null -w 'flv:%{http_code} bytes:%{size_download}\n' \
  http://192.168.2.198:8080/live/main.flv
```

Expected: `a013f167`; `active` = `b`; no `trial-*`; three ports up; ffprobe reports
`h264` with real dimensions; FLV returns bytes.

**STOP the entire rollout if any of these fail.** Go to Task 6.

**Step 6: Record the result**

Note the version, active slot, and stream check in your working notes. `.198`
passing is what authorises Tasks 3–5.

## Task 3: Upgrade `.146` (jumphost, exFAT, healthiest)

`.146` goes first behind the jumphost: 8-day uptime, newest deployed build, and
its applier already carries the `remove_tree` fix. It proves the bundle on exFAT
with the least to lose.

**Step 1: Open the tunnel and confirm identity**

```bash
ssh -o BatchMode=yes -o ExitOnForwardFailure=yes -f -N \
  -L 12446:192.168.30.146:24 root@192.168.3.137
uv run python3 scripts/debugging/cam_exec.py --host 127.0.0.1 --port 12446 \
  'ifconfig wlan0 | head -2 | tail -1'
```

Expected: `inet addr:192.168.30.146`.

**STOP if it prints any other address.** A pre-existing tunnel owns port 12446 and
every following command would silently hit the wrong camera. Kill the stale
forward (`pkill -f 12446:192.168.30`) and reopen.

**Step 2: Read `active` and derive the inactive slot**

```bash
uv run python3 scripts/debugging/cam_exec.py --host 127.0.0.1 --port 12446 \
  'cat /mnt/anyka_hack/active; echo; ls /mnt/anyka_hack/slots'
```

Expected: `b`, and slots `a a.preidr b b.aside b.aside2`.

**The inactive slot is the letter that is NOT printed by `active`.** With
`active=b`, the inactive slot is `a`. Never hardcode this — a camera that
self-reverted mid-rollout flips to `a`, and an `rm -rf slots/a` issued from a
stale assumption would delete the *running* slot out from under live processes.

**Step 3: Fix the stale NTP server**

`.146` still points at `192.168.3.1`, the gateway of a network it no longer lives
on. Its clock is correct today only because the `0.ubuntu.pool.ntp.org` fallback
works.

```bash
uv run python3 scripts/debugging/cam_exec.py --host 127.0.0.1 --port 12446 \
  'cp /mnt/anyka_hack/anyka.toml /mnt/anyka_hack/anyka.toml.pre-a013f167 && sed -n "75p" /mnt/anyka_hack/anyka.toml'
```

Expected: `servers = ["192.168.3.1", "0.ubuntu.pool.ntp.org"]`

**STOP if line 75 is anything else** — the file has shifted and the edit below
would corrupt the wrong line.

```bash
uv run python3 scripts/debugging/cam_exec.py --host 127.0.0.1 --port 12446 \
  'busybox sed -i "75s|192\.168\.3\.1\"|192.168.30.1\"|" /mnt/anyka_hack/anyka.toml && sync && sed -n "74,76p" /mnt/anyka_hack/anyka.toml'
```

Expected: line 75 now reads `servers = ["192.168.30.1", "0.ubuntu.pool.ntp.org"]`,
with lines 74 and 76 unchanged.

This is device-local config, deliberately excluded from the bundle, so it survives
the upgrade. `[time]` is read by `anyka-init` at boot, so the upgrade's own reboot
is what activates it — no separate reboot needed.

**Step 4: Clear the inactive slot and sweep leftovers**

```bash
uv run python3 scripts/debugging/cam_exec.py --host 127.0.0.1 --port 12446 \
  'cd /mnt/anyka_hack/slots && busybox rm -rf a a.preidr b.aside b.aside2 && sync && ls'
```

Expected: only `b` remains.

Rust's `remove_dir_all` fails on these exFAT cameras, the old applier swallows
that error with `let _ =`, and the following `rename` then fails with
`File exists (os error 17)`. `busybox rm -rf` on the same path works. Doing this
unconditionally means we do not care which applier version is running.

This does **not** cost the automatic rollback: the applier stages into `a` and
flips to it, and a failed trial flips back to `b`, which still holds the build the
camera is running right now.

**Step 5: Upload**

```bash
cd /home/kmk/dev/anyka-dev
./scripts/upload_upgrade_bundle.sh --host 192.168.30.146 \
  --jumphost root@192.168.3.137 --user admin \
  --pass-file <(printf %s "$CAMERA_PASS") /tmp/bundle-a013f167.tar
```

Expected: **HTTP 202**. The script stages the credential in a netrc on the
jumphost, curls from there, and wipes it — no password reaches argv on either
host.

**Step 6: Wait, then wait for it to answer**

Wait 150 seconds, then poll from the jumphost:

```bash
ssh -o BatchMode=yes root@192.168.3.137 'for i in $(seq 1 30); do code=$(curl -s -o /dev/null -m 5 -w "%{http_code}" http://192.168.30.146/ || true); echo "attempt $i: $code"; [ "$code" = "200" ] && break; sleep 10; done'
```

Expected: `200` within a few attempts.

The tunnel from Step 1 dies with the reboot. Reopen it before any telnet command.

**Step 7: Verification gate**

```bash
# version + ports, from the jumphost
ssh -o BatchMode=yes root@192.168.3.137 "curl -s -u admin:'$CAMERA_PASS' http://192.168.30.146/api/diagnostics" | jq -r .firmware_version
ssh -o BatchMode=yes root@192.168.3.137 'for p in 80 554 8080; do nc -z -w3 192.168.30.146 $p && echo "$p up" || echo "$p DOWN"; done'

# reopen tunnel, then slot state
ssh -o BatchMode=yes -o ExitOnForwardFailure=yes -f -N -L 12446:192.168.30.146:24 root@192.168.3.137
uv run python3 scripts/debugging/cam_exec.py --host 127.0.0.1 --port 12446 \
  'ifconfig wlan0 | head -2 | tail -1; cat /mnt/anyka_hack/active; echo; ls /mnt/anyka_hack/state/trial-* 2>/dev/null; echo TRIAL_CHECK_DONE; date; sed -n "75p" /mnt/anyka_hack/anyka.toml'
```

Expected: `a013f167`; ports 80/554/8080 up; `wlan0` still `.146`; `active` = `a`;
no `trial-*`; `date` still correct; NTP line still points at `192.168.30.1`.

Stream check from the jumphost:

```bash
ssh -o BatchMode=yes root@192.168.3.137 'curl -s -m 8 -o /dev/null -w "flv:%{http_code} bytes:%{size_download}\n" http://192.168.30.146:8080/live/main.flv'
```

Expected: HTTP 200 with a non-zero byte count.

**STOP the rollout if any check fails.** Go to Task 6.

## Task 5: Upgrade `.127` (jumphost, exFAT, config drift)

`.127` goes last: it has the most unknown recent history (13 minutes of uptime at

Expected: `inet addr:192.168.30.127`. **STOP on any other address.**

Note the uptime. If it is again only a few minutes, the camera is rebooting on a
cycle — investigate before upgrading, because an upgrade into a reboot loop
cannot pass its trial window.

**Step 2: Back up both config files**

This camera's history earns the insurance.

```bash
uv run python3 scripts/debugging/cam_exec.py --host 127.0.0.1 --port 12427 \
  'cp /mnt/anyka_hack/anyka.toml /mnt/anyka_hack/anyka.toml.pre-a013f167 && cp /mnt/anyka_hack/onvif/config.toml /mnt/anyka_hack/onvif/config.toml.pre-a013f167 && sync && ls -la /mnt/anyka_hack/*.pre-a013f167 /mnt/anyka_hack/onvif/*.pre-a013f167'
```

**Step 3: Set the clock immediately**

The camera reads 1970. Fix it now, without a reboot, so every later verification
runs against a sane clock:

```bash

```

Expected: `date -u` now returns the real UTC time.

At 1970 the clock is not cosmetic: `ws_security` rejects every authenticated ONVIF
request on ±300 s skew, so ONVIF verification would fail for reasons unrelated to
the build. `PUT /api/update` uses HTTP Basic and is unaffected, which is exactly
how a broken clock stays hidden.

Expected: line 75 now `enabled = true`, lines 74 and 76 unchanged.

## Task 6: Failure handling (reference — do not run unless a gate fails)

| Symptom | Diagnosis | Action |
|---|---|---|
| HTTP 409 on upload | Spool busy | `ls -la /mnt/anyka_hack/spool` — remove a stale `bundle.tar.part`; if `bundle.trigger` exists an apply is already queued, wait it out |
| HTTP 401 | Credentials | Check `CAMERA_PASS`; the account must be Administrator |
| HTTP 413 | Bundle over the 64 MB ceiling | Rebuild; check nothing dragged `lib/` in |
| `File exists (os error 17)` in the device log | The `rm -rf` hit the wrong slot, or was skipped | Re-read `active`, delete the *other* slot, re-upload |
| Camera returns on the OLD version | Trial failed and self-reverted | **Stop the rollout.** Read `/mnt/logs/anyka-init.log` for the failing port. Do not re-upload the same tar |
| HTTP dead, telnet alive | `onvif-rust` down | FTP the bundle to `/mnt/anyka_hack/spool/bundle.tar`, then `touch /mnt/anyka_hack/spool/bundle.trigger` **last** |
