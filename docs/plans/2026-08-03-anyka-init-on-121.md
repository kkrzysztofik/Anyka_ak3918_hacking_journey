# anyka-init Cutover on Camera .121 — Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Move camera `192.168.30.121` off `gergehack.sh` onto the `anyka-init` Rust boot supervisor, without stranding a camera that has no serial console and whose only recovery is pulling the SD card on-site.

**Architecture:** `.121`'s P0 wrapper becomes the same `SD_card_contents/Factory/config.sh` that `.198` already runs, plus a wifi deadman that hands the radio back to the vendor chain if nothing holds an IP three minutes after boot. Its `anyka.toml` is `.198`'s file with four deltas (sensor path, SSID, NTP server, and a new `[services.ptz]`). The irreversible step — overwriting `config.sh` on the SD card — happens last, after a full dry run proves the configuration on the live camera.

**Tech Stack:** POSIX shell (busybox ash), Rust 2021 (`anyka-init`, host tests only), TOML config, telnet-over-SSH device access.

**Design doc:** `docs/plans/2026-08-03-anyka-init-on-121-design.md`

## Background you need before starting

**Device access.** `.121` is reachable *only* through a jumphost:

```bash
ssh root@192.168.3.137        # then, from there:
telnet 192.168.30.121 24      # root, empty password
```

A plain `telnet host 24 < script` closes the session. Drive it with a helper that pipes a here-doc through the login prompts. Create `/tmp/ak121.sh`:

```bash
#!/bin/bash
# usage: ak121.sh <command-file> [wait-seconds]
CMDFILE="$1"; WAIT="${2:-8}"
ssh -o BatchMode=yes root@192.168.3.137 "
  { printf 'root\n'; sleep 1; printf '\n'; sleep 1; cat <<'AKEOF'
$(cat \"\$CMDFILE\")
AKEOF
    sleep $WAIT; printf 'exit\n'; sleep 1; } | telnet 192.168.30.121 24 2>&1
"
```

`chmod +x /tmp/ak121.sh`. Write each batch of commands to a file and pass it; do not try to inline quoted commands, they get mangled.

`.198` is the working reference and is reachable directly: `telnet 192.168.2.198 24`.

**Rust toolchain.** Use the vendored cargo for everything:

```bash
toolchain/arm-anykav200-crosstool-ng/bin/cargo test \
  --target x86_64-unknown-linux-gnu --manifest-path cross-compile/anyka-init/Cargo.toml
```

Host-side Rust **always** needs `--target x86_64-unknown-linux-gnu`; without it cargo cross-compiles for ARM and the tests will not run.

**The rule that matters most.** Until Task 6 writes the new `config.sh`, a power cycle is a complete rollback — the camera boots straight back into the vendor stack. After Task 6, it is not. Do not reorder these tasks.

## Task 2: Add the wifi deadman

`main.rs:16` parks forever on a config error, and wifi bring-up is P2 at `main.rs:62` — so a bad config leaves telnet listening on an interface with no link. On `.198` that is survivable; on `.121` it means an on-site SD pull. The deadman closes that gap.

It is harmless on `.198` too (the `grep` matches, nothing runs), so it goes in the one shared tracked file rather than a `.121` variant.

**Files:**
- Modify: `SD_card_contents/Factory/config.sh` (before the final `exec`)
- Create: `cross-compile/anyka-init/tests/p0_wrapper.rs`

**Step 1: Write the failing test**

Create `cross-compile/anyka-init/tests/p0_wrapper.rs`:

```rust
//! The P0 wrapper is the one file whose failure cannot be fixed remotely:
//! .121 has no serial console and recovery means pulling the SD card on-site.
//! These tests run the shipped script under `sh` with stubbed helpers so both
//! deadman branches are exercised exactly as written.

use std::fs;
use std::os::unix::fs::PermissionsExt;
use std::path::{Path, PathBuf};
use std::process::Command;

fn script() -> PathBuf {
    Path::new(env!("CARGO_MANIFEST_DIR"))
        .join("../../SD_card_contents/Factory/config.sh")
}

/// Write an executable stub into `dir`.
fn stub(dir: &Path, name: &str, body: &str) -> PathBuf {
    let path = dir.join(name);
    fs::write(&path, format!("#!/bin/sh\n{body}\n")).expect("write stub");
    fs::set_permissions(&path, fs::Permissions::from_mode(0o755)).expect("chmod stub");
    path
}

/// Run the wrapper with `ifconfig` reporting `has_ip`, and report whether the
/// deadman invoked the vendor wifi chain.
fn run(has_ip: bool) -> bool {
    let tmp = tempfile::tempdir().expect("tempdir");
    let dir = tmp.path();

    // `sleep 180` would make the test take three minutes.
    stub(dir, "sleep", "exit 0");
    stub(dir, "telnetd", "exit 0");
    let ifconfig_out = if has_ip { "inet addr:192.168.30.121" } else { "" };
    stub(dir, "ifconfig", &format!("echo '{ifconfig_out}'"));

    let marker = dir.join("vendor-wifi-started");
    let wifi_manage = stub(
        dir,
        "wifi_manage.sh",
        &format!("touch '{}'", marker.display()),
    );
    // The supervisor never returns in production; exiting keeps the test bounded.
    let init_bin = stub(dir, "anyka-init.bin", "exit 0");

    let status = Command::new("sh")
        .arg(script())
        .env("PATH", format!("{}:/usr/bin:/bin", dir.display()))
        .env("ANYKA_INIT_BIN", &init_bin)
        .env("ANYKA_WIFI_MANAGE", &wifi_manage)
        .status()
        .expect("run config.sh");
    assert!(status.success(), "wrapper must exit 0 when the binary is present");

    // The deadman is a backgrounded subshell; give it a moment to finish.
    std::thread::sleep(std::time::Duration::from_millis(300));
    marker.exists()
}

#[test]
fn deadman_stays_quiet_when_the_interface_has_an_address() {
    assert!(
        !run(true),
        "wlan0 has an IP, so the vendor chain must not be started"
    );
}

#[test]
fn deadman_restores_vendor_wifi_when_the_interface_has_no_address() {
    assert!(
        run(false),
        "no IP after the delay must hand wifi back to the vendor chain"
    );
}

#[test]
fn wrapper_fails_loudly_when_the_supervisor_binary_is_missing() {
    let tmp = tempfile::tempdir().expect("tempdir");
    let dir = tmp.path();
    stub(dir, "sleep", "exit 0");
    stub(dir, "telnetd", "exit 0");
    stub(dir, "ifconfig", "echo ''");

    let status = Command::new("sh")
        .arg(script())
        .env("PATH", format!("{}:/usr/bin:/bin", dir.display()))
        .env("ANYKA_INIT_BIN", dir.join("does-not-exist"))
        .env("ANYKA_WIFI_MANAGE", dir.join("does-not-exist"))
        .status()
        .expect("run config.sh");
    assert!(!status.success(), "a missing supervisor must be a loud failure");
}
```

**Step 2: Run the tests to verify they fail**

## Task 3: Confirm ptz_daemon_dyn survives supervision

`gergehack.sh` starts PTZ with `&` via `run_ptz.sh`. anyka-init's supervisor expects a foreground process — if `ptz_daemon_dyn` daemonises and its parent exits, the supervisor sees an immediate exit and will restart it until the crashloop guard trips. Find out before writing the service entry.

**Files:** none — this is a device check.

**Step 1: Check whether it stays in the foreground**

```bash
cat > /tmp/c-ptz.txt <<'EOF'
killall ptz_daemon_dyn 2>/dev/null
sleep 1
export LD_LIBRARY_PATH=/mnt/anyka_hack/ptz/lib
/mnt/anyka_hack/ptz/ptz_daemon_dyn &
FGPID=$!
sleep 3
echo "spawned=$FGPID"
ps | grep ptz_daemon_dyn | grep -v grep
EOF
/tmp/ak121.sh /tmp/c-ptz.txt 14
```

Expected, if it behaves: `ps` shows a `ptz_daemon_dyn` whose PID **equals** `spawned`. That means it does not fork, and supervision works.

If the PID differs — it daemonised. Do **not** add `[services.ptz]`; record the finding in the design doc's out-of-scope section and leave PTZ unmanaged for now. The rest of the cutover is unaffected. A supervised daemonising process is a crashloop, which on `.121` costs three reboots before safe mode parks it.

**Step 2: Restore the running daemon**

```bash
cat > /tmp/c-ptz2.txt <<'EOF'
killall ptz_daemon_dyn 2>/dev/null
/mnt/anyka_hack/ptz/run_ptz.sh
sleep 2
ps | grep ptz_daemon_dyn | grep -v grep
EOF
/tmp/ak121.sh /tmp/c-ptz2.txt 12
```

Expected: one `ptz_daemon_dyn` running.

## Task 5: Dry run on the camera

`config.sh` stays untouched for this whole task, which is what keeps a power cycle as a complete rollback.

**Step 1: Upload the config**

```bash
ftp -n 192.168.30.121 <<'EOF'
user root <REDACTED: FTP password from secret store, never commit>
binary
put .deploy/anyka-121.toml /mnt/anyka_hack/anyka.toml
bye
EOF
```

If `.121` is not directly routable from your host, copy to the jumphost first and run the FTP from there.

**Step 2: Verify it parses**

```bash
cat > /tmp/c-parse.txt <<'EOF'
ls -l /mnt/anyka_hack/anyka.toml
timeout 5 /mnt/anyka_hack/anyka-init.bin
echo "exit=$?"
EOF
/tmp/ak121.sh /tmp/c-parse.txt 14
```

Expected: **no** `config load failed` line. A parse error prints `anyka-init: config load failed: …` and then parks — which is why `timeout` wraps it. If you see that message, fix `.deploy/anyka-121.toml` and repeat; do not continue.

A clean parse means it proceeded into P2 and started reconfiguring wifi, so expect the session to drop. That is fine at this stage — the vendor chain is still installed and the link returns.

**Step 3: Stop everything the supervisor will own**

```bash
cat > /tmp/c-stop.txt <<'EOF'
killall app_restarter.sh 2>/dev/null
killall libre_anyka_app 2>/dev/null
killall onvif-rust.bin 2>/dev/null
killall vendor-daemon.bin 2>/dev/null
killall ptz_daemon_dyn 2>/dev/null
killall ntpd 2>/dev/null
killall wifi_run.sh 2>/dev/null
sleep 2
fuser /dev/video0
ps | grep -v "\[" | grep -v grep
EOF
/tmp/ak121.sh /tmp/c-stop.txt 14
```

Expected: `fuser /dev/video0` returns nothing, and `telnetd` is still in `ps`. Kill `app_restarter.sh` **first** — it polls every 20 s and respawns `libre_anyka_app`, which grabs `/dev/video0` and makes VI fail with `VIDIOC_S_FMT, Device or resource busy`.

**Step 4: Arm the deadman by hand and launch detached**

```bash
cat > /tmp/c-run.txt <<'EOF'
# Two-stage deadman, matching the shipped config.sh. Stage two (restore the
# vendor boot path and reboot) is omitted here: config.sh.gerge.bak does not
# exist until Task 6 Step 1, and the dry run must not reboot the camera.
( sleep 180
  ifconfig wlan0 | grep -q "inet addr" && exit 0
  /usr/sbin/wifi_manage.sh start
  sleep 60
  ifconfig wlan0 | grep -q "inet addr" && exit 0
  echo "two-stage deadman: second check still dead" ) &
cd /mnt/anyka_hack
nohup ./anyka-init.bin > /mnt/logs/anyka-init-dryrun.log 2>&1 &
echo "launched pid=$!"
EOF
/tmp/ak121.sh /tmp/c-run.txt 6
```

The session will drop: P2 rmmods and reinserts `ssv6355.ko`, taking the link down. That is expected — it is also the only way the deadman gets exercised. Do not try to watch it live.

**Step 5: Wait 90 seconds, then reconnect and check the pass criteria**

```bash
sleep 90
cat > /tmp/c-verify.txt <<'EOF'
echo "=== wifi ==="
ifconfig wlan0 | head -3
grep -i "wifi up\|chip\|driver" /mnt/logs/anyka-init.log | tail -5
echo "=== modules ==="
lsmod
echo "=== processes ==="
ps | grep -v "\[" | grep -v grep
echo "=== video owner ==="
fuser /dev/video0
echo "=== encoders ==="
grep "grp_type" /mnt/logs/vendor_daemon.log | tail -4
echo "=== listeners ==="
netstat -ltn | head
echo "=== storm state ==="
cat /mnt/anyka_hack/state/boot.json
EOF
/tmp/ak121.sh /tmp/c-verify.txt 18
```

Pass criteria — **all** must hold before Task 6:

- `wlan0` has an `inet addr`
- log shows `wifi up` with `chip=ssv6355_ble` and `driver=wext`
- `lsmod` lists `sensor_gc1084`, `akcamera`, `ak_info_dump`, `ssv6x5x`
- `anyka-init.bin`, `vendor-daemon.bin`, `onvif-rust.bin` running (plus `ptz_daemon_dyn` if Task 3 allowed it)
- `fuser /dev/video0` returns the vendor-daemon PID only
- both `grp_type=1` and `grp_type=2` appear in recent encoder lines
- `:80` is bound
- `boot.json` reads `{"fast_reboots":0,"wifi_reboots":0}`

Note which of these the deadman had to rescue. If `wifi_manage.sh` started the radio rather than anyka-init, the supervisor's wifi path failed — diagnose that before proceeding, since after Task 6 you would be relying on the deadman every boot.

The shipped deadman is **two-stage**: at T+180 s it retries the vendor Wi-Fi chain (`wifi_manage.sh start`); if `wlan0` still has no address T+60 s later it restores `config.sh.gerge.bak` over `config.sh` (atomically: copy to a temp path, sync, rename) and reboots. The dry run above exercises stage one; stage two is exercised after the cutover, since it needs the `.bak` that Task 6 Step 1 creates.

**Step 6: Abort path**

If anything fails and the camera is unreachable, a power cycle restores the vendor stack completely — `config.sh` is untouched. If it is reachable but wrong, `reboot` does the same.

## Out of scope

The open `:554` bind failure and the `ak_vi_get_frame` / `H264EncStrmEncode` frame starvation on `.121` are not addressed here, and none of the pass criteria depend on them. Gating a boot-path change on a pre-existing streaming bug would block the deploy on an unrelated fix.

`/mnt/anyka_hack/lib/` on `.121` holds 4 files against `.198`'s 11. The supervisor runs, so nothing it needs is absent, but that divergence deserves its own reconciliation.
